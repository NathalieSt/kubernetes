# MEMORY.md — context for AI models working in this repo

Read this before making changes.

Full documentation: the `homelab-docs` repo
(`docs/03-kubernetes-manifests.md` in particular).

## What this repo is

The GitOps state that FluxCD reconciles onto a k3s homelab cluster. Everything
under `cluster/` is **generated output**, not source.

## The one rule that matters

**Do not hand-edit generated manifests.** They are produced by the
`Nathi/kubernetes-generator` repo and overwritten wholesale on its next CI run.
A fix applied here disappears the moment anything upstream changes.

To change what the cluster runs, change the generator:

| Want to change | Edit, in kubernetes-generator |
| --- | --- |
| An image or chart version | `versions/{apps,infrastructure,monitoring}.json` |
| A workload's spec | `internal/generators/<category>/<name>/manifests.go` |
| Namespace, exposure, scaling, dependencies | that generator's `main.go` |
| The Flux Kustomization set | it is emitted from `GeneratorMeta.Flux`; edit the generator |

Then push — CI regenerates and opens a PR here.

The commit history contains a few direct hand-edits (`fix forgejo version`,
`shorten forgejo labels`). Those are mistakes to learn from, not a pattern to
follow.

## What is *not* generated

Two exceptions, and they are the only files here it is legitimate to edit
directly:

- **`cluster/flux/flux-system/`** — `gotk-components.yaml`, `gotk-sync.yaml`,
  `kustomization.yaml`. Written by `flux bootstrap` and marked
  "generated by flux. DO NOT EDIT". Changing these is a Flux CLI operation.
- **`cluster/apps/technitium/`** — hand-written manifests for the DNS server,
  not yet migrated to a generator. It has no entry in the generated
  `cluster/flux/apps.yaml`, so it is not reconciled by the generated
  Kustomization set.

### `cluster/flux/image-automation/` is gone — do not reinstate it

There was a third exception until September 2026: an `ImageUpdateAutomation`
with `ImagePolicy`/`ImageRepository` pairs for adguard-home, jellyfin,
cert-manager and nfs-subdir-external-provisioner.

It had done nothing for a long time and nothing said so. Setters-strategy
automation rewrites values marked with a `# {"$imagepolicy": ...}` comment, and
there was not one such marker anywhere under `cluster/` — so every run
reconciled successfully, reported "repository up-to-date", and wrote nothing.
Two of the four apps no longer had generators at all. What it did still have
was push access to `main` of this repo, aimed at the `GitRepository`'s URL —
the Codeberg mirror — so had it ever started writing it would have written to
the mirror and forked the two remotes.

Image versions are pinned in `kubernetes-generator/versions/*.json` and that is
the only path. Note for anyone tempted to bring setters back against those
files: the marker is a YAML comment and those files are JSON, which has no
comments. Automating bumps means either converting them to YAML or doing it in
the generator's CI.


## Layout

```
cluster/
  flux/
    apps.yaml            generated — one Kustomization per app generator
    infrastructure.yaml  generated
    monitoring.yaml      generated
    flux-system/         Flux bootstrap output (not ours)
  apps/ infrastructure/ monitoring/
                         one directory per generator, matching its Flux `path`
```

Each leaf directory holds its generator's output plus a `kustomization.yaml`
listing the files.

## How reconciliation works

- `GitRepository` `flux-system` — branch `main`, 1m interval.
- Root `Kustomization` `flux-system` — path `./cluster/flux`, 10m interval,
  prune on.
- Per-generator Kustomizations — 24h interval, `prune: true`, `wait: true`,
  `timeout: 10m`, with a `dependsOn` graph. `flux-notifications` is the one
  exception: it uses `wait: false` with explicit `healthChecks`, because part
  of its inventory cannot be healthy until a human has put a token in Vault.

`wait: true` means `dependsOn` waits for **health**, not just application. A
wedged dependency stalls everything downstream — usually the right behaviour,
and usually the reason a rollout looks stuck. It is also not free when it goes
wrong: a Kustomization that can never pass its health checks holds a
kustomize-controller worker for its full 10m timeout on every retry, which is
what the `--concurrent=10` patch in `flux-system/kustomization.yaml` was added
to survive.

## Failures are reported now — they were not before

Until September 2026 the notification-controller had no `Provider` and no
`Alert`, so Flux failed silently: at the time this was set up, 18 of 59
Kustomizations were not Ready — one stalled dependency cascading through
fourteen, plus a genuinely failed Deployment — and nothing had said so.

Two paths now, both emitted by the `flux-notifications` generator:

- **Events** → an `alertmanager` Provider pointing at the VMAlertmanager in the
  victoria-metrics stack, so Flux failures group and silence with everything
  else. A second `gitea` Provider posts a commit status onto the Forgejo commit
  each reconciliation came from.
- **Metrics** → a `VMRule` in `flux-system`.

The metrics half is worth knowing about in detail, because the obvious query is
wrong: **`gotk_reconcile_condition` and `gotk_suspend_status` no longer exist.**
The controllers exported them until Flux 2.6; on 2.7 (kustomize-controller
v1.7.3 here) the only `gotk_` series on `/metrics` are reconcile durations and
the token cache. Flux resource state now comes from kube-state-metrics reading
the CRs, configured in the victoria-metrics generator
(`flux-resource-state.yaml`), and arrives as `gotk_resource_info` — an Info
metric whose value is always 1 and whose state is in labels (`ready`,
`suspended`, `customresource_kind`).

The Perses "GitOps Delivery" dashboard had been built on the removed metrics
and its two headline panels had been rendering empty for however long. A metric
that stops existing does not produce an error anywhere; check before trusting a
quiet panel.

The 24h interval is not slow reconciliation: Git pushes drive changes, and the
interval is only the drift-correction backstop.

```sh
flux get kustomizations --watch
flux reconcile kustomization <name> --with-source
kubectl describe kustomization <name> -n flux-system
```

## Verify before trusting this repo as "what runs"

Two things to check, because both have been wrong:

1. **The Flux source URL — and the mirror hop.**
   `cluster/flux/flux-system/gotk-sync.yaml` points the root `GitRepository` at
   `ssh://git@codeberg.org/NathalieStiefsohn/kubernetes.git`, while CI opens
   its PRs against `my-homelab/kubernetes` on the Forgejo. Both are real: the
   Codeberg repo is a **push mirror** of the Forgejo one, so a change reaches
   the cluster as generator CI → Forgejo PR → merge → mirror push → Codeberg →
   the `GitRepository`'s 1m poll. Verified in September 2026 by matching the
   revision the cluster reported against the Forgejo merge commit that produced
   it — the SHAs are preserved across the mirror.

   That extra hop looks like something to remove, and it is **deliberate**.
   Flux's source must not be anything Flux manages: Forgejo runs in this
   cluster, so pointing the `GitRepository` at it would mean a broken Forgejo
   takes with it the cluster's ability to reconcile its way back to health. An
   external mirror is what keeps recovery possible. The same reasoning is why
   there is no `Receiver`/webhook — the webhook would have to come from the
   Forgejo side, and its push cannot help until the mirror has the commit
   anyway.

   The consequence to hold in mind is the lag: a merge is not immediately in
   the cluster's source, so `git log origin/main` on Forgejo can be ahead of
   what Flux has seen.
2. **Freshness.** As of the last review this checkout had no `garage`, `k8up`
   or `backup-dashboard` anywhere under `cluster/`, although all three exist as
   generators upstream. `git fetch && git log --oneline HEAD..origin/main`
   before assuming the tree is current.

## Check any new `.gitignore` pattern against the generated tree

A git pattern with no slash in it matches at **every depth**, and CI's
`git add -A` skips ignored paths in silence. A bare `vault-backup`, meant to
block a Vault dump pulled out of the cluster during recovery, therefore also
swallowed `cluster/infrastructure/vault-backup/` — the directory the
vault-backup generator writes its K8up Schedule into. The generator produced it
on every run, CI never committed it, and Flux reported the Kustomization as
`ArtifactFailed: kustomization path not found`.

What that cost: **Vault had no backup.** Its namespace had the Garage bucket,
the scoped access key and the out-of-band restic password all provisioned and
27 days old — every part of the design except the one object that runs it. The
Schedule was simply absent from the cluster, and nothing said so until Flux
alerting was switched on. Vault holds every other secret in this homelab.

The pattern is now `/vault-backup`, anchored to the repo root. Before adding
another, check it:

```sh
for f in $(cd ../kubernetes-generator && find cluster tofu -type f); do
  git check-ignore -q "$f" && echo "IGNORED: $f"
done
```

## Secrets

No secret material belongs here. `.gitignore` blocks `caddy-server.p12`,
`root.crt`, `root.key` and `/vault-backup` specifically because those get pulled
out of the cluster during recovery work and are easy to commit by accident.

Secrets reach workloads through Vault + the Vault Secrets Operator, and
config templates containing placeholders are substituted by init containers at
pod start — so the rendered values never enter this repo's history. Keep it
that way.
